# Realtime Lab Files

Obsidian sync for Markdown, images, PDF, DOCX and supported opaque files. Install through BRAT using `ns19920320-cyber/obsidian-realtime-lab-files`. Each vault requires its own authenticated server space. Keep LiveSync disabled in a vault using this plugin. Existing nonempty uninitialized vaults are not automatically adopted or overwritten.

The Files plugin entry point is `src/v3/plugin.ts`, its manifest is `manifest.v3-files.json`, and its build command is `npm run build:v3-files`. Use the Files build explicitly. `src/plugin.ts`, `build.mjs` and the generic `npm run build` belong to the legacy V2 implementation; do not use them to build Files. Root installation assets can lag an unreleased source branch.

## Development

Use Node.js 22 and `npm ci`, then:

```sh
npm run typecheck
node --test --test-concurrency=1 test/*.test.mjs
npm run build:v3-files
node scripts/check-v3-release.mjs
```

Assets are generated in `work/v3-files-plugin/`. Test with synthetic files and an independent server directory; never point automated tests at an existing vault or server store. Do not commit settings, vault contents, caches, runtime directories or credentials.

## Versions and recovery

`0.5.0-alpha.26` preserves the document and durable queues while reconnecting after foreground wake; offline progress is explicitly stale. The alpha.26 Release `source.zip` is the exact source used for that published build. This repository now contains the editable source; earlier autogenerated tag archives can point to older publication commits. Existing published tags/releases are retained without rewriting history.

See `SOURCE-MAP.md` for source ownership and the release checklist, and `V3-FILES.md` for protocol details. `ARCHITECTURE.md`, `NATIVE-V3.md` and other older documents contain historical milestones; current limits and behavior are defined by the V3 source and tests.

See [SERVER-BACKUPS.md](SERVER-BACKUPS.md) for the independent verified snapshot, retention, scheduled watcher and restore drill. These local server tools do not require a phone plugin update and do not enable backups in existing production services automatically.

## Desktop background sync

From alpha.37, desktop clients use a native Node timer to check connections and
refresh remote diagnostics about every 10 seconds even when the window is hidden.
Due retries retain their original ledger and versions. Mobile clients still need
the foreground. OS sleep, process suspension and quitting Obsidian stop execution;
no power blocker or background service is installed. Diagnostic reports keep the
real visibility flag; an older server's completion summary may still require the
foreground even when background connection and queue reports are fresh.

## Deleted-name recreation (alpha.46)

Newly created files retain the exact observed deletion generation in the durable pending manifest. A matching alpha.46 server is required to publish these recreations. Older servers leave the local file and cached pending version intact. Concurrent recreation or a newer deletion requires review and does not overwrite another device. Legacy files with no creation evidence are retained under consistency protection. Existing history and caches are preserved.

## File moves (alpha.47)

Moves explicitly reported by Obsidian use one protected batch, including large folder moves. Durable backups and exact source-version/target checks remain mandatory. Receiving devices remove the old local path only after a unique matching new copy is present and verified; ambiguous copies remain under review. Separate deletion/creation events are shown as possible moves and grouped by source folder for review. Existing unapproved plans are never automatically approved or cancelled. Waiting for a decision is displayed separately from a stalled transfer.

## Capacity planning

Alpha.48 servers default to 1 GiB of active logical content and 2 GiB of retained blob storage. Client private caches default to 2 GiB. Metadata is bounded at 8 MiB; streaming, per-file, path-count and object-count limits remain enforced. Budgets do not reserve memory or preallocate disk. No history or cached payload is automatically removed to meet a limit.

The sync details and supported remote diagnostics show separate content, retained storage, metadata, path and object usage; client cache use is included once measured. At 80% a warning is shown, and a full budget stops the affected publication while retaining its immutable queued version. A server may override the defaults with a validated `capacity.json` beside its token (fields `liveBytes` and `diskBytes`); restart it after backing up. Boundaries are 1 MiB–4 GiB active and active-budget–8 GiB storage. Physical free disk must also be available.

Recognized capacity retries resume after sufficient space or budget is available. Unknown, authentication and identity errors remain blocked; existing unapproved path plans are never approved, cancelled or bypassed by capacity recovery. Legacy clients may continue within their existing receive window; above it the server asks for an upgrade before sending an oversized snapshot. Upgrading a client alone does not change an older server's active-content budget.

## Queue classification (alpha.49)

Sync details and the note badge distinguish awaiting confirmation, protection deferral and actual failures. Counts use unique paths; retained version counts are shown separately. Groups of path plans retain their own group count. Protected versions remain in the original durable pending manifest and cache, and do not count as completed synchronization.

Stale per-path failures remain stored but are excluded from live failure totals, unknown-error diagnostics, stalled-transfer checks and retry timers while their paths are awaiting confirmation or held. Manual retry does not rearm those protected records. Real errors on other paths and global connection/local errors remain visible. Explicitly removing protection exposes the original retry state again; this release never approves or cancels existing plans. New servers support optional count-only queue diagnostics; older servers continue to receive the compatible existing status fields.
